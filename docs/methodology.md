# Methodology

This document defines everything behind the README figures and
[the showcase report](reports/showcase.md): the data, the strategy, the execution model,
every metric, the validation methods and the checks that guard them. The code is the
reference; each section names the module it describes.

Methodology version 1.0. The version (`METHODOLOGY_VERSION` in `src/research/showcase.py`)
changes whenever a metric definition, validation method or consistency check here changes.
Every report manifest records it, together with this document's fingerprint.

## Evidence categories

Every figure carries a tag in its top-right corner that says what kind of evidence it is.

| Tag | Meaning | Used for |
| --- | --- | --- |
| `SYNTHETIC DATA · SIMULATED EXECUTION` | A backtest of generated prices through the simulated broker | Tear sheet, attribution, trades, drawdowns, distribution, exposure, walk-forward, robustness, uncertainty |
| `MODELED · …` | A calculation on top of a simulation, with stated assumptions | Capacity curve; also the fitted normal and Student-t tails and the bootstrap inside other figures |
| `MEASURED · THIS MACHINE` | Timings and memory taken on the machine that ran the generator | Engineering benchmarks |

With `--dataset`, the data part of the tag comes from the dataset manifest's `origin`.
Nothing in this repository is paper trading or live trading.

The synthetic universe contains no predictable returns, so a positive backtest on it says
nothing about whether the strategy works. It shows that the engine, the accounting and the
reports behave correctly on realistic-looking data with known properties.

## Data

### Synthetic universe (`src/research/datasets.py`)

`synthetic_universe_v1` holds daily bars for eight equity-like instruments from 2019-01-01
to 2023-12-29 on a Monday–Friday calendar without holidays (1,304 bars). It is generated by
`generate_synthetic_universe()` with seed `20261120` and stored in
[`data/demo/synthetic_universe_v1/`](../data/demo/synthetic_universe_v1/) together with its
specification and SHA-256 checksums. None of its values was chosen by looking at strategy
results.

The data-generating process, with `Δt = 1/252`:

```text
regime s_t        two-state Markov chain: P(stay calm) = 0.985, P(stay turbulent) = 0.95
                  vol scale k_t = 1 (calm) or 2.25 (turbulent)
market factor     m_t = 0.06·Δt + 0.16·√Δt · k_t · ε_t
sector factor     f_t = 0.10·√Δt · k_t · ε'_t                       (one per sector)
log return        r_it = β_i·m_t + λ_i·f_sector(i),t + σ_i·√Δt · (1 + 0.5·(k_t − 1)) · η_it
close             P_it = P_i0 · exp(Σ r_it)
```

`ε`, `ε'` and `η` are independent Student-t draws with 5 degrees of freedom, rescaled to
unit variance. Calm spells last 67 bars on average and turbulent ones 20, so about 23% of
days are turbulent. Idiosyncratic volatility rises by a smaller factor (1.625) than the
factors in turbulent periods.

| Symbol | Sector | β | Sector loading λ | Idiosyncratic vol σ (calm) | Typical volume |
| --- | --- | ---: | ---: | ---: | ---: |
| TEC_A | Technology | 1.25 | 0.8 | 22% | 4.0M |
| TEC_B | Technology | 1.15 | 0.8 | 26% | 3.0M |
| FIN_A | Financials | 1.05 | 0.7 | 18% | 6.0M |
| FIN_B | Financials | 1.10 | 0.7 | 21% | 5.0M |
| NRG_A | Energy | 0.80 | 1.0 | 24% | 3.5M |
| HLT_A | Healthcare | 0.70 | 0.6 | 17% | 2.5M |
| UTL_A | Utilities | 0.45 | 0.5 | 13% | 2.0M |
| NEW_A | none | 1.30 | 0.0 | 35% | 1.5M |

Open, high, low and volume are derived from the close with extra noise (opens gap by
`0.3·r + 0.2·σ·z`, highs and lows widen by `0.4·σ·|z|`, volume scales with `|r|/σ`). Prices
are rounded to cents. The strategy reads closes only; volumes feed the capacity model.

Three data-quality cases are built in, and the reports have to handle them visibly:

- **Late listing:** NEW_A starts trading on 2021-01-04.
- **Missing classification:** NEW_A has no sector; exposure figures group it as
  "Unclassified".
- **Halts:** TEC_B has no bar on five days (2020-03-24, 2020-04-10, 2020-04-13, 2022-02-09,
  2022-05-31). Open positions keep their last close as the mark, and orders wait for the
  next bar of that symbol.

**Why nothing is predictable.** Drift is constant and the shocks are independent given
the regime. The regime changes volatility, never the expected return, so past returns
carry no information about future returns. Volatility *is* persistent, which the
inverse-volatility weights can use to control risk, but that does not create an expected
return. Because the market drift is positive, a portfolio that is net long on average
earns some of that drift; that is exposure, not skill.

The parameters are per 252 bars, while the calendar has about 261 bars per year. Measured
per calendar year, the market drift is therefore 6.2% and the calm market volatility 16.3%.

`python scripts/generate_readme_assets.py --regenerate-dataset` rebuilds the files from the
specification; the checksums in `manifest.json` (computed with LF line endings) must match.

### Your own data

`load_dataset()` reads any directory with this layout and validates it before a backtest
sees it:

| File | Required | Content |
| --- | --- | --- |
| `prices.csv` | yes | `date, symbol, open, high, low, close, volume`; one row per symbol and day |
| `instruments.csv` | no | `symbol, sector, listed_from`; an empty sector counts as unclassified |
| `manifest.json` | no | `name`, `origin` (e.g. `historical market data`), `currency`, `calendar`, and `files` with SHA-256 checksums, which are verified |
| `regimes.csv` | no | `date, regime`; only the synthetic generator knows regimes |

Each symbol's dates must be unique and increasing, prices finite and positive, and high
and low must bracket open and close. The pipeline expects daily bars: the annualization
check stops the run unless there are 240–270 observations per year.

```powershell
python scripts/generate_readme_assets.py --dataset D:\data\my_universe --assets-dir build\report\assets --reports-dir build\report
```

README.md is only updated for the default dataset. `build/` and everything under `data/`
except `data/demo/` are ignored by Git, so licensed data and its results stay local.

## Strategy: `tsmom-1.0` (`src/research/strategies.py`)

A time-series momentum rule with inverse-volatility weights, long and short:

```text
signal_i   = sign( ln(P_t / P_t−L) )                      L = lookback = 60 bars
vol_i      = standard deviation of the last 60 daily log returns
raw_i      = signal_i / vol_i
weight_i   = clip( raw_i · 1.0 / Σ|raw_j| , −0.25, +0.25 ) gross target 1.0, cap 25%
```

- It rebalances every 5 bars (`R5`), and only instruments with at least 61 closes take part.
- Orders move each position to `weight × equity / close` whole shares. Trades smaller than
  0.5% of equity are skipped.
- All orders are market orders.

The parameters (L60-R5, volatility window 60, gross 1.0, cap 25%, minimum trade 0.5%)
were written into the code before the first backtest ran and have not been changed. The
labels call this "pre-registered"; there is no external registry. Other settings appear
only in the robustness and walk-forward analyses.

## Execution model (`src/backtesting/engine.py`)

- **Timing.** On each bar the strategy sees closes up to and including that bar. Orders it
  returns fill at the **next bar of the same symbol**, at that bar's close moved
  **5 bps against the trader**.
- **Costs.**
  - Commission is **10 bps of fill notional**.
  - Slippage is part of the fill price; the reports show it as a cost component and never
    deduct it a second time.
- **Not modeled:**
  - Partial fills, volume limits and market impact. Impact appears only in the capacity
    model.
  - Interest on cash, financing of leverage, borrow fees and dividends.
  - Short-sale proceeds are credited to cash and earn nothing.
- **Ledger.** Every bar records cash, equity, quantities and the mark of every position:
  - If an instrument has no bar (a halt), its last close is carried forward and flagged
    as stale.
  - Every order is logged as accepted or rejected, with a reason.

The run starts at the first bar with capital USD 1,000,000. It stays flat for 61 bars
while the signal warms up, and those bars are part of the statistics.

## Metrics (`src/analytics/`)

Returns are simple daily returns of net equity, `r_t = E_t / E_{t−1} − 1`. Annualization
uses the observed frequency:

```text
years = (last date − first date) in days / 365.25
ppy   = (number of equity points − 1) / years        ≈ 261.1 here, ≈ 252 with exchange holidays
```

A fixed 252 would misstate the volatility of the Monday–Friday calendar by about 1.8%.

| Metric | Definition |
| --- | --- |
| Total return | `E_N / E_0 − 1` |
| CAGR | `(E_N / E_0)^(ppy / n) − 1`, equal to compounding over calendar years |
| Volatility | `sd(r) · √ppy`, sample standard deviation |
| Sharpe ratio | `mean(r) / sd(r) · √ppy`, risk-free rate 0% because cash earns nothing in the simulation |
| Sortino ratio | `mean(r) / √mean(min(r, 0)²) · √ppy` (target return 0) |
| Max drawdown | `min(E / running max(E) − 1)` |
| Calmar ratio | `CAGR / abs(max drawdown)` |
| Hit rate | Share of positive days among days with a non-zero return |
| Skewness, excess kurtosis | Bias-corrected sample moments of `r` |
| Benchmark | Equal-weight index of the instruments that traded that day, rebalanced daily, frictionless. A halted day contributes no return, and the gap return is taken on the day trading resumes. |
| Beta, correlation | `cov(r, b) / var(b)` and the Pearson correlation on common dates |
| Tracking error | `sd(r − b) · √ppy` |
| Information ratio | `mean(r − b) · ppy / tracking error` |
| Rolling volatility / Sharpe | 63-bar and 126-bar windows |
| Monthly returns | Daily returns compounded within each month and year |
| Turnover | Traded notional / mean equity / years |

**Drawdown episodes.**
- An episode starts at the last peak before equity falls below it, has its trough at the
  lowest point, and ends on the first bar that regains the peak.
- Durations are counted in bars.
- An episode still open at the end is reported as not recovered.
- The maximum drawdown is the depth of the deepest episode. Its peak, trough, recovery date
  and recovered status are all read from that one episode (`deepest_episode` in
  `drawdowns.py`), never from the latest episode.
- Ties: if several episodes have exactly the same depth, the earliest (by peak date) is the
  maximum drawdown. That is where the running drawdown first reaches its minimum, so the
  episode's depth equals the reported value; the generator stops if the two differ.
- Without any episode (equity never below a previous peak) the maximum drawdown is 0 and the
  report says there was no drawdown.

**Distribution.** Empirical VaR and expected shortfall come from the sample (historical
simulation). The normal and Student-t curves are maximum-likelihood fits; they are models,
not observations.

**Exposure.**
- Weights are signed position values divided by equity.
- Long, short, gross (`long − short`) and net (`long + short`) exposures are sums of
  weights.
- The effective number of positions is `(Σ|w|)² / Σw²`.
- Return correlations need at least 126 overlapping days per pair, so NEW_A's short
  history cannot pass for a reliable estimate.

**P&L attribution** (`attribution.py`). For fill `i` with signed quantity `q` (+buy,
−sell), reference close `r`, fill price `p`, commission `c`, and final position `Q`
marked at `M`:

```text
frictionless P&L = Σ(−q·r) + Q·M            trading at the reference closes
slippage cost    = Σ q·(p − r)              already inside the fill prices
net P&L          = frictionless − slippage − commissions = final equity − initial capital
```

Per-instrument rows sum to the portfolio. Financing is reported as not modeled rather than
as zero.

**Trades** (`trades.py`).
- An order is a request, a fill is an execution, and a closed trade is a first-in,
  first-out match between an opening and a closing fill.
- Rebalancing trims positions, so one fill can close several lots and one lot can be
  closed by several fills.
- Commissions are allocated per share to both legs.
- Break-even lots count as neither wins nor losses.
- Closed-lot P&L plus open-lot P&L at the final marks equals net P&L.

## Validation

**Parameter sweep.**
- Lookbacks 10, 20, 40, 60, 120 and 250 × rebalance intervals of 1, 5, 10 and 21 bars:
  24 runs over the whole sample with the same costs.
- Each run is isolated (its own engine and strategy) and optionally runs in its own
  process.
- A run that fails stays in the table with its error; none failed in the published run.

**Walk-forward.**
- Windows: 504 training bars (about two years), then 126 evaluation bars (about six
  months), rolling by 126. The last window absorbs any remaining bars.
- In each window, all 24 configurations run on the training bars, and the one with the
  highest in-sample Sharpe ratio (net of costs) runs unchanged on the evaluation bars.
- Every evaluation run starts flat with the initial capital. History before it is read
  for signals only, never traded.
- The out-of-sample curve joins the evaluation windows' daily returns.
- Picking the best of 24 configurations inflates in-sample Sharpe ratios by construction;
  the gap between in-sample and out-of-sample results measures that inflation together
  with any lack of predictability.

**Bootstrap** (`uncertainty.py`).
- Method: a Politis–Romano stationary bootstrap of the main run's daily net returns, with
  geometric block lengths (mean 21 bars) and circular wrap-around.
- Size: 5,000 one-year paths of 261 bars, seed `20261121`.
- Output: the distributions of one-year return, maximum drawdown and Sharpe ratio, and the
  share of losing years.
- The paths reshuffle the observed history, so they inherit its length, its regimes and
  its luck. They are not a forecast.

**Regimes.** Performance split by the generator's calm/turbulent label. The labels exist
only for synthetic data.

**Capacity** (`capacity.py`). The capacity curve is a cost model, not a simulation.
- **Scaling.** Each observed fill is re-priced at larger capital, assuming every order
  scales linearly and the strategy does not adapt.
- **Impact.** On top of commission and slippage, square-root market impact is charged per
  fill: `impact = Y · σ · √(shares / ADV) · notional`.
  - `σ` (daily return volatility) and `ADV` (mean daily volume) come from the 20 bars
    before the fill.
  - `Y` is 0.5, 1 or 2.
- **Participation** is fill shares / volume of the fill bar.
- Even the base-capital row includes modeled impact that the simulation did not charge.

## Run identity and reproducibility

- **Run id.**
  - The first 10 hex digits of a SHA-256 hash over the dataset checksum, strategy version,
    parameters, execution settings and the run window.
  - The same inputs always give the same id, and any change gives a new one.
  - It identifies the inputs, not the code: the source fingerprint (below) does that.
- **Randomness.**
  - Only two seeds are used: `20261120` for the dataset and `20261121` for the bootstrap.
  - The engine itself is deterministic.
  - The number of worker processes (`--jobs`) does not change results.
- **Manifest.** `docs/reports/showcase/manifest.json` records:
  - the configuration and the dataset checksums;
  - every run id and the checks;
  - the machine and library versions (`environment`);
  - the `provenance` block described below.
- **Figures.**
  - Same inputs, same bytes. The PNGs carry no timestamps, and the 256-color palette
    reduction is deterministic.
  - Engineering benchmarks are measured afresh unless `--reuse-engineering` loads
    `engineering.json`.

### Provenance (`src/research/provenance.py`)

The manifest's `provenance` block identifies the code, dependencies and inputs behind a
report.

**Fingerprints.** Every fingerprint is the SHA-256 of a file's contents after removing a
UTF-8 byte-order mark and converting CRLF and CR line endings to LF. A Windows checkout with
`core.autocrlf=true` and a Linux checkout of the same commit give the same values. The
dataset checksums use the same normalization.

**Source fingerprint scope.** The README asset generator and every package it runs:

| Pattern | Contents |
| --- | --- |
| `scripts/generate_readme_assets.py` | The generator |
| `src/analytics/**/*.py` | Metric calculations |
| `src/backtesting/**/*.py` | Backtest engine and simulated broker |
| `src/core/**/*.py` | Models, configuration and event bus used by the engine |
| `src/reporting/**/*.py` | Figures, tables and report text |
| `src/research/**/*.py` | Datasets, strategy, experiments, checks, benchmarks, provenance |
| `src/services/**/*.py` | Live services timed by the order-to-portfolio benchmark |

- `source.files` lists each file with its hash. `source.fingerprint` is the SHA-256 of the
  sorted lines `<path> NUL <hash> LF` (repository-relative paths with `/`), so it depends on
  file names and contents only, not on timestamps, the checkout location or Git.
- `tests/unit/test_provenance.py` follows every `src` import of the generator, including
  imports inside functions, and fails if a module it reaches is out of scope.
- Excluded: everything else, in particular what the generator writes (figures, reports, CSV
  tables, the manifest, `engineering.json`, the generated blocks in `README.md`), datasets
  (fingerprinted as inputs, below), tests, caches (`__pycache__`) and temporary files.
  Regenerating artifacts therefore never changes the fingerprint, and no recorded hash
  covers a file that records it.

**Source commit.** `source.commit` is the full SHA of the most recent commit that changed a
file in scope. `source.clean` says whether the files in scope match that commit exactly; if
they do not, `source.uncommitted_files` lists the files that differ, and the fingerprint,
not the commit, identifies the code. The commit is deliberately not `HEAD`: committing the
regenerated artifacts on top does not change it, so the same source and inputs give the
same provenance, and the same manifest, on every rerun in the same environment. Without Git
these fields are empty.

**Dependencies.** `dependencies.specifications` fingerprints `pyproject.toml`,
`requirements_engine.txt` and `requirements_reports.txt` (`requirements_dev.txt` only adds
Django and test tools to them). `dependencies.installed` records the Python version and the
installed numpy, pandas, scipy, matplotlib, Pillow, contourpy, kiwisolver and fonttools,
plus the FreeType library bundled with matplotlib.

**Inputs and versions.** `inputs` fingerprints each dataset file the run read (`prices.csv`,
`instruments.csv`, `regimes.csv`, `manifest.json`). `versions` records the strategy
version, the methodology version and this document's fingerprint.

To publish a report whose manifest names a clean commit, commit the source changes first,
then regenerate, then commit the regenerated files.

## Consistency checks (`src/research/showcase.py`)

The generator stops with exit code 1 and writes no figures, tables or report if any check
fails.

| Check | Passes when |
| --- | --- |
| Business-day calendar | Timestamps are unique, increasing and never on a weekend |
| Annualization | 240–270 observations per year, and CAGR equals calendar-year compounding within 1e−9 |
| Equity finite and positive | Every equity value is finite and above zero |
| Ledger identity | Equity equals cash plus positions at their marks on every bar, within 1e−6 |
| No missing marks | Every open position has a mark (carried-forward closes are counted and reported) |
| P&L decomposition reconciles | Frictionless − slippage − commissions equals the equity change within 0.01 |
| FIFO trades reconcile | Closed-lot plus open-lot P&L equals the equity change within 0.01 |
| Slippage counted once | Attributed slippage equals the executions' slippage, which sits inside fill prices |
| Finite headline metrics | Total return, CAGR, volatility, Sharpe, Sortino, max drawdown and beta are finite |
| Benchmark alignment | Every strategy return date has a benchmark return |
| Walk-forward separation | Each evaluation window starts after its training window and after the previous evaluation window |
| Sweep accounted for | The sweep table has one row per grid point, failed runs included |
| No strategy errors | The main run raised no strategy errors |

`tests/unit/test_research_analytics.py` covers the definitions above on small hand-checkable
inputs, and `tests/unit/test_backtest_engine.py` covers the ledger, missing marks and
rejected orders.

## Engineering benchmarks (`src/research/benchmarks.py`)

- **Backtest scaling.**
  - Workload: momentum backtests on synthetic universes of 1, 4 and 16 instruments ×
    252, 504, 1,008 and 2,016 bars.
  - Each size runs three times; the figure shows the median, and memory is the
    `tracemalloc` peak.
- **Event bus.** 20,000 `InMemoryEventBus.publish` calls with three async subscribers.
- **Order to portfolio.**
  - 2,000 orders through the engine's services: `OrderExecutionService.submit_order` →
    risk check → simulated engine (no fill delay) → event bus → portfolio update.
  - Everything runs in one process.

The CPU, memory, operating system and library versions are stored with the results. The
numbers describe one machine and one Python process, not a production system.

## Known limitations of the method

- Daily bars, next-close fills and fixed costs: there are no intraday effects, queues,
  partial fills or volume caps in the simulation.
- No financing, borrow costs or dividends; cash earns nothing.
- One strategy family on one synthetic universe. The showcase demonstrates tooling, not
  an investable result.
- The bootstrap is conditional on five years of one synthetic history.
- The capacity curve is a model with stated parameters, not an observation.
